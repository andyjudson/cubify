## Summary

Add Scramble and Solve buttons to the cubify-harness `index.html`.
Scramble generation ships two modes: `CubeScramble.random()` (default — instant,
pure JS) and `CubeScramble.wca()` (optional — WCA random-state quality via the
twips WASM already vendored in cubing.js). A toggle in the harness switches
between them. Solve runs a purpose-built Kociemba 2-phase IDA* implementation in
a web worker (`solver.worker.ts`), which posts `progress` events at each depth
iteration — driving a progress bar in the UI. `CubeSolver` and the new
`CubeScramble.wca()` method are both added to `packages/cubify/src/`. The harness
case selector gains a `— scramble —` placeholder selected whenever Scramble is pressed.

**Hard prerequisite**: `specs/cubing-js-solver.md` — produced during planning
of this feature. ✅ Written.

**Scale/Scope**: Single 3×3 solver instance per harness session; Phase 1 is harness-only

## Constitution Check

### Gate 1 — Module boundaries
**Pass.** `CubeSolver` is a new module; it reads `KPattern.patternData` (public API) and uses `KTransformation` internally for move table generation. It does not reach into `CubeRenderer3D`, `CubePlayer`, or `CubeState` internals.

### Gate 2 — No cubing.js exposure to consumers
**Pass.** `CubeSolver` uses cubing.js KTransformation internally to build move tables; this is an implementation detail. The public `CubeSolver` API takes `KPattern` (already a cubify-wrapped type from `CubeState`) and returns `{ alg: string }`.

### Gate 3 — Harness-first
**Pass.** Full integration validated in `cubify-harness/index.html` before any cfop-app work.

### Gate 4 — Rendering invariants
**Pass.** Solver runs in a web worker; it has no access to the Three.js scene graph. The main thread only calls `player.state` (read-only) and `player.loadAlg()` after the solution arrives. No rendering code is touched.

### Gate 5 — No new npm dependencies
**Pass.** The 2-phase solver is pure TypeScript. Move tables are built using cubing.js KTransformation objects (already a dependency).

## Phase 1: Design

### 2-Phase algorithm overview

**Phase 1** reduces to the H subgroup (all edges and corners oriented, UD-slice
edges in slice). Three coordinates:
- CO (corner orientation): 3^7 = 2187 states
- EO (edge orientation): 2^11 = 2048 states
- UD-slice (UD-slice edge positions): C(12,4) = 495 states

**Phase 2** solves within H using only (U, D, R2, L2, F2, B2). Three coordinates:
- CP (corner permutation): 8! = 40320 states
- EP-slice (UD-slice edge permutation): 4! = 24 states
- EP-UDE (U/D edge permutation): 8! = 40320 states

**Pruning tables**: populated by BFS from solved state. Give IDA* a lower bound
on remaining depth for each coordinate.

**Move tables**: precomputed for all 18 moves × all coordinate states, using
cubing.js KTransformation composition for correctness.

### Module responsibilities

| Module | Responsibility |
|--------|---------------|
| `Coordinates.ts` | Encode/decode CO, EO, UDSlice, CP, EP-slice, EP-UDE from KPatternData |
| `MoveTables.ts` | Build `moveTable[coord][moveIdx] → newCoord` using KTransformations |
| `TwoPhase.ts` | IDA* search across Phase 1 + Phase 2 with pruning table lookups |
| `solver.worker.ts` | Message protocol; timeout guard; calls TwoPhase and posts progress |
| `CubeSolver.ts` | Main-thread API; constructs/manages worker; exposes `solve()` Promise |

### Harness additions

In `cubify-harness/index.html`:

- Case selector gains `<option value="scramble">— scramble —</option>` as first entry; Scramble button selects it
- **Random/WCA toggle** (radio buttons or segmented control): selects scramble source; defaults to Random
- **Scramble button**: calls `CubeScramble.random(20)` or `CubeScramble.wca()` depending on toggle; passes result as setup to `player.loadAlg('', scramble)`; sets selector to `scramble`; WCA path shows brief loading state on first call (WASM lazy-load)
- **Solve button**: calls `solver.solve(player.state)` → gets solution alg → calls `player.loadAlg(solutionAlg)` and plays; disabled while solve in progress
- **Progress bar**: `<progress max="20" value="0">` updated on each `{ type: 'progress', depth }` event from worker
- **Event log**: each `progress` event appends a line (`Solver: searching depth N…`); solution arrival logs the alg and elapsed time; errors (timeout, unavailable) log the reason — no inline error text near the controls

### KPattern → worker data transfer

```typescript
// Extract from player.state (CubeState wraps KPattern)
const raw = player.state.toRawPattern();  // or player.state.patternData
const msg = {
  type: 'solve',
  stateData: {
    CORNERS: {
      pieces:      raw.patternData['CORNERS'].pieces,
      orientation: raw.patternData['CORNERS'].orientation,
    },
    EDGES: {
      pieces:      raw.patternData['EDGES'].pieces,
      orientation: raw.patternData['EDGES'].orientation,
    },
  },
};
worker.postMessage(msg);
```

Plain object — transfers via structured clone without issue.

### Vitest unit tests (`cube-solver.test.ts`)

- Coordinate round-trips: encode → decode solved state, each single-move state
- Move table correctness: applying move R to each coordinate matches cubing.js
  ground truth
- Known solutions: assert `solve(solved)` = `""`, `solve(R U R' U')` ≤ 4 moves
- Timeout: assert solve with 1 ms timeout rejects with `'timeout'`
